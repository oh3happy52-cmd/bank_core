# 2주차 정리: 동시성 제어 방식 비교와 선택

- 실험 일시: 2026-10-27
- 테스트: `TransferLockBenchmarkTest.세_가지_방식을_같은_조건에서_반복_측정한다`
- 환경: Spring Boot 4.1.2, MySQL 8.4 (Testcontainers), 격리 수준 REPEATABLE READ, HikariCP 기본 설정(커넥션 10개)

## 측정 방법

- 동일 출금 계좌에 1,000원 이체 요청 100건을 스레드 32개로 동시 실행
- 각 방식 워밍업 1회(결과 제외) 후 5회 측정
- 회차마다 실행 순서를 돌려 순서에 따른 영향을 줄임
- 한 번의 실행, 같은 테스트 DB에서 모든 방식을 측정
- 모든 회차에서 성공 100건, 잔액 정확성 검증 통과

## 결과

| 방식 | 평균 | 최소 ~ 최대 | 평균 재시도 | 측정값 (ms) |
|---|---|---|---|---|
| 비관적 락 | 1,016ms | 738 ~ 1,469ms | 0회 | 809, 1469, 1286, 778, 738 |
| 원자적 UPDATE | 1,218ms | 518 ~ 2,087ms | 0회 | 1004, 2087, 1296, 1189, 518 |
| 낙관적 락 + 재시도 | 2,384ms | 1,306 ~ 4,063ms | 765회 | 2284, 4063, 1796, 2474, 1306 |

## 해석

- 정합성: 세 방식 모두 갱신 손실 없이 잔액이 정확했음
- 낙관적 락 + 재시도: 평균 처리 시간이 다른 방식의 약 2배, 요청당 평균 약 7.7회 재시도
  → 같은 계좌에 요청이 몰리는(충돌이 잦은) 상황에는 적합하지 않음
- 비관적 락 vs 원자적 UPDATE: 측정값 범위가 크게 겹쳐 5회 측정으로는 유의미한 차이를 확인하지 못함
- 이전 1회 측정에서 원자적 UPDATE가 비관적 락보다 약 2배 빨랐던 것은, 비관적 락 측정이 워밍업 없이 첫 실행이었던 영향이 컸던 것으로 판단
- 원자적 UPDATE는 락 구간이 짧은 대신, 거래 후 잔액 확인을 위한 재조회 등 SQL이 더 많아 장단점이 상쇄된 것으로 추정

## 최종 선택: 비관적 락

| 기준 | 판단 |
|---|---|
| 정합성 | 세 방식 동일 |
| 처리 시간 | 비관적 락 ≈ 원자적 UPDATE < 낙관적 락 + 재시도 |
| 규칙 관리 | 비관적 락은 출금, 입금 규칙(금액, 계좌 상태, 잔액)을 Account 엔티티에 모아 둘 수 있음. 원자적 UPDATE는 규칙이 서비스와 SQL로 흩어짐 |
| 확장성 | 이체 한도 등 규칙이 추가될 때 엔티티에 추가하기 쉬움 |

- 이체 API(`POST /api/v1/transfers`)와 입금 API 모두 비관적 락 사용
- 데드락 방지를 위해 두 계좌를 항상 계좌번호 오름차순으로 잠금
- 낙관적 락, 원자적 UPDATE 구현은 비교 실험용으로 유지

## 알려진 한계

- 모든 입금이 시스템 계좌(SYS-CASH) 한 행을 잠그므로, 입금 요청이 매우 많아지면 이 행에 대기가 몰리는 핫스팟이 될 수 있음
- 5회 측정은 표본이 적음. 측정 횟수를 늘리면 비관적 락과 원자적 UPDATE의 차이가 드러날 수도 있음
- 단일 서버, 단일 DB 환경의 측정이며, 서버를 여러 대로 늘린 환경은 측정하지 않음

# 3주차 요약: 에러 응답, 멱등성, 원장 검증, 정산 배치

## 1. 목표
- 에러가 나면 항상 같은 모양으로, 원인을 구분할 수 있게 응답한다
- 같은 요청이 여러 번 와도 돈은 한 번만 옮긴다 (멱등성)
- 잔액과 원장이 항상 맞는지 검사할 수 있게 한다
- 하루치 거래를 매일 자동으로 정산한다

## 2. 공통 에러 응답
응답 = HTTP 상태 코드(큰 분류) + `code`(정확한 원인) + `message`(사람이 읽는 설명)

| 요청 | 수정 전 | 수정 후 |
|---|---|---|
| 잔액보다 큰 금액 이체 | 500 | 422 `INSUFFICIENT_BALANCE` |
| 없는 계좌 조회 | 500 | 404 `ACCOUNT_NOT_FOUND` |
| 금액 0원 이체 | - | 400 `INVALID_REQUEST` |
| `Idempotency-Key` 없이 이체 | - | 400 `MISSING_IDEMPOTENCY_KEY` |

자세한 내용: `week3-error-response.md`

## 3. 멱등성
| 상황 | 수정 전 | 수정 후 |
|---|---|---|
| 같은 키 + 같은 내용 재요청 | 500 (이미 성공한 입금을 실패처럼 응답) | 201, 처음과 같은 transferId, 잔액 변화 없음 |
| 같은 키 + 다른 금액 | 500 | 422 `IDEMPOTENCY_KEY_REUSED` |
| 같은 키 10건 동시 도착 | - | 성공 1 / 409 9 / 기타 0, 잔액 +1,000원 (1번만) |

- 두 겹 방어: ① 돈을 옮기기 전에 키 조회 → ② DB `UNIQUE(idempotency_key)`가 최종 방어선
- 동시 도착은 둘 다 ①을 통과하므로 ②가 반드시 필요 (테스트에서 10건 모두 ①을 통과, ②가 9건 차단)

자세한 내용: `week3-idempotency.md`

## 4. 원장 정합성 검증
`GET /api/v1/admin/ledger/verification`

| 검사 | 정상이면 |
|---|---|
| 1. 계좌마다 잔액 = 장부 합계 (`LEFT JOIN` + `CASE` + `HAVING`) | 불일치 계좌 없음 |
| 2. 전체 잔액 합계 | 0 (SYS-CASH가 내준 만큼 마이너스) |
| 3. 완료된 이체마다 장부 2줄, DEBIT = CREDIT | 문제 이체 없음 |

| 실험 | 검사 1 | 검사 2 | 검사 3 |
|---|---|---|---|
| 정상 거래만 | 통과 | 0 | 통과 |
| 이영희 잔액만 장부 없이 +500원 | 100-0002 적발 (잔액 500, 장부 0) | 500 | 통과 |

- 3개 검사가 서로 다른 종류의 사고를 잡으므로 같이 실행
- 3개 SQL을 readOnly 트랜잭션 하나로 실행 → REPEATABLE READ에서 같은 시점의 데이터를 봄
- 실제 서버 DB: `consistent: true`

## 5. 일일 정산 배치
- 테이블: `daily_settlement` (Flyway V3), `UNIQUE(settlement_date)`로 하루 한 줄
- 자동 실행: `@Scheduled(cron = "0 5 0 * * *", zone = "Asia/Seoul")` → 매일 00:05에 어제 정산
- 수동 실행: `POST /api/v1/admin/settlements?date=YYYY-MM-DD` (실패 시 운영자가 재실행)
- 하루 범위: `[그날 00:00, 다음날 00:00)`, 완료(COMPLETED)된 거래만

| 확인 | 결과 |
|---|---|
| 어제 입금 2건 + 이체 1건, 오늘 입금 1건 | 어제 정산: 입금 2건 80,000원, 이체 1건 20,000원 (오늘 거래 제외) |
| 같은 날짜 두 번 정산 | 같은 결과(id 동일), 저장된 줄 1개 |
| 오늘 날짜 정산 | 400 `SETTLEMENT_DATE_NOT_CLOSED` |
| 실제 서버: 10월 28일 정산 | 입금 1건 1,000원, 원장 검사 PASSED |

## 6. 트러블슈팅
| 문제 | 원인 | 해결 |
|---|---|---|
| 에러 응답 추가 후에도 curl 결과가 전부 500 | `Account`, `AccountService`가 예전 예외를 던짐 | 서버 로그의 클래스·줄 번호로 확인 후 `BusinessException`으로 교체 |
| 오늘 날짜를 정산해서 "0건"이 저장됨 | 안 끝난 날을 정산하면 이후 거래가 빠지고, 멱등성 때문에 다시 계산되지 않음 | 어제 이전만 허용(400), 잘못 저장된 줄 삭제 |
| 테스트 간 DB 오염 가능성 | 2주차 데드락 실험 코드가 원장 없이 잔액만 바꿈 | 정합성·정산 테스트 전후로 DB 초기화 |
| 테스트가 시작도 못 하고 실패 | Docker Desktop이 꺼져 있음 | Docker 켜고 재실행 |

## 7. 판단 근거
- **키 확인을 돈 옮기기 전에**: 뒤에 두면 이미 잠금·변경을 한 뒤라 늦다
- **재요청에 에러 대신 처음 결과**: 재요청한 앱은 첫 응답을 못 받은 상태라, 에러를 주면 성공을 실패로 오해한다
- **Spring Batch 대신 `@Scheduled`**: 하루 1번, 집계 SQL 하나로 끝나는 작업이라 충분하다
- **정산 시각 00:05**: 자정 직전에 시작한 거래가 커밋을 마칠 여유를 준다

## 8. 한계
- 멱등성 키 보관 기간 제한(예: 24시간 후 만료)은 구현하지 않음
- 서버 여러 대면 각 서버의 스케줄러가 모두 실행됨 (결과는 UNIQUE로 한 줄이지만, 실서비스라면 분산 락 필요)
- 정산의 원장 검사는 "그날"이 아니라 정산 시점의 전체 원장을 검사함

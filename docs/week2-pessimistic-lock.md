# 2주차 (1): 비관적 락으로 갱신 손실 해결

- 실험 일시: 2026-10-27
- 테스트: `TransferPessimisticLockTest.비관적_락으로_동시에_100번_이체하면_잔액이_정확하다`
- 환경: Spring Boot 4.1.2, MySQL 8.4 (Testcontainers), 격리 수준 REPEATABLE READ, HikariCP 기본 설정

## 적용 방법

- 계좌 조회 시 `@Lock(LockModeType.PESSIMISTIC_WRITE)`로 `SELECT ... FOR UPDATE` 실행
- 트랜잭션이 끝날 때까지 해당 계좌 행에 배타 락(X lock) 유지
- 데드락 방지를 위해 두 계좌를 항상 계좌번호 오름차순으로 잠금

## 실험 조건

- 1주차와 동일: 출금 계좌에 100,000원 입금 후, 1,000원 이체 요청 100건을 스레드 32개로 동시 실행

## 결과

| 항목 | 락 없음 (1주차) | 비관적 락 |
|---|---|---|
| 성공 / 실패 | 100 / 0 | 100 / 0 |
| 출금 계좌 잔액 (기대 0원) | 90,000원 | 0원 |
| 입금 계좌 잔액 (기대 100,000원) | 10,000원 | 100,000원 |
| 처리 시간 | 미측정 | 2,641ms (1회 측정) |

원본 출력:
```
========== 동시성 실험 결과 (비관적 락) ==========
요청 수          : 100
성공 / 실패      : 100 / 0
출금 계좌 기대 잔액 : 0  →  실제: 0
입금 계좌 기대 잔액 : 100000  →  실제: 100000
처리 시간        : 2641 ms
=================================================
```

## 분석

- 실행된 SQL에 `for update`가 포함되어 행 잠금이 적용됨을 확인
- 트랜잭션이 같은 계좌를 순서대로 처리하여 항상 최신 잔액 기준으로 계산 → 갱신 손실 없음
- 대기가 발생하므로 동시 처리량은 줄어듦. 처리 시간은 1회 측정값이라 비교에는 여러 번 측정한 평균 필요

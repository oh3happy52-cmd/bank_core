# 3주차 ② 멱등성 (Idempotency-Key)

## 1. 왜 했나
- 앱이 이체 요청을 보냈는데 응답이 오는 중에 네트워크가 끊기면, 앱은 성공/실패를 모르고 **같은 요청을 다시 보낸다.**
- 대책이 없으면 **이체가 2번** 처리된다.

## 2. 규칙
앱은 사용자가 버튼을 누를 때마다 새 `Idempotency-Key`를 만들고, 재전송할 때는 같은 키를 쓴다.

| 상황 | 서버 동작 |
|---|---|
| 처음 보는 키 | 정상 처리 (201) |
| 같은 키 + 같은 내용 | 돈을 다시 옮기지 않고 **처음 결과를 그대로** 돌려줌 (201, 같은 transferId) |
| 같은 키 + 다른 내용 | 422 `IDEMPOTENCY_KEY_REUSED` |
| 같은 키가 동시에 도착 | 먼저 저장한 1건만 성공, 나머지는 409 `DUPLICATE_REQUEST` |

- "내용이 같은지"는 요청 내용을 SHA-256으로 만든 `request_hash`로 비교한다.

## 3. 구현 (두 겹 방어)
1. **1차: 서비스 0단계** — 계좌를 잠그기 전에 `findByIdempotencyKey`로 키를 먼저 찾는다.
   돈을 옮기기 **전에** 확인해야 불필요한 잠금과 롤백이 없다.
2. **최종: DB UNIQUE 제약** (`uk_transfer_idempotency_key`) — 동시에 들어와 둘 다 1차를 통과해도, 저장 시점에 하나만 성공한다.
   `GlobalExceptionHandler`가 이 제약 위반만 골라 409로 바꾼다. (다른 제약 위반은 버그일 수 있으므로 500 + 에러 로그)

## 4. 수정 전 문제 (재현)
- 같은 키로 입금 2번 → 1번째 201, 2번째 **500** `INTERNAL_ERROR`, 잔액은 +1,000 (1번만)
- 돈은 DB UNIQUE 규칙 덕분에 안전했지만, **이미 성공한 입금을 실패처럼 알려 주는** 문제가 있었다.
- 또 돈을 다 옮긴 뒤에 롤백하므로 계좌를 쓸데없이 잠갔다.

## 5. 확인 결과
**curl**
| 요청 | 결과 |
|---|---|
| `idem-001` + 1,000원 재요청 | 201, transferId 5 (처음과 같음), 잔액 변화 없음 |
| `idem-001` + 5,000원 | 422 `IDEMPOTENCY_KEY_REUSED` |

**동시성 테스트** (`TransferIdempotencyTest`, 같은 키로 입금 요청 10건 동시 실행)
| 항목 | 결과 |
|---|---|
| 성공 / 충돌(409) / 기타 | 1 / 9 / 0 |
| 성공 응답의 transferId | 1종류 |
| 잔액 변화 | +1,000 (기대: +1,000) |

## 6. 판단 근거
- **키 확인을 돈 옮기기 전에 둔 이유**: 뒤에 두면 이미 잠금·변경을 한 다음이라 늦다.
- **UNIQUE 제약을 남긴 이유**: 서비스의 확인만으로는 "동시에 확인 → 둘 다 없음"을 막을 수 없다. DB가 최종 방어선이다.
- **재요청에 에러 대신 처음 결과를 주는 이유**: 재요청한 앱은 첫 응답을 못 받은 상태다. 에러를 주면 성공한 거래를 실패로 오해한다.

## 7. 한계
- 동시 도착 시 늦은 요청은 409를 받는다. 앱이 잠시 후 같은 키로 다시 보내면 처음 결과(201)를 받는다.
- 키 보관 기간 제한(예: 24시간 후 만료)은 구현하지 않았다.

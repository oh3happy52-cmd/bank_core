# 2주차 (3): 원자적 UPDATE로 갱신 손실 해결

- 실험 일시: 2026-10-27
- 테스트: `TransferAtomicUpdateTest.원자적_UPDATE로_동시에_100번_이체하면_잔액이_정확하다`
- 환경: Spring Boot 4.1.2, MySQL 8.4 (Testcontainers), 격리 수준 REPEATABLE READ, HikariCP 기본 설정(커넥션 10개)

## 적용 방법

- Java에서 잔액을 계산하지 않고, DB에 계산식을 보내 DB가 직접 계산하게 함
- `AccountRepository`에 JPQL로 UPDATE 쿼리 작성 (`@Modifying` + `@Query`)
  ```
  update Account a set a.balance = a.balance - :amount, a.version = a.version + 1
  where a.id = :id and a.balance >= :amount
  ```
  - 실제 실행 SQL: `update account set balance=(balance-?), version=(version+1) where id=? and balance>=?`
  - 잔액이 부족하면 조건에 맞지 않아 수정된 행 수가 0 → 예외를 던져 트랜잭션 롤백
  - `@Version` 자동 검사를 거치지 않으므로 버전 번호를 직접 1 증가 (낙관적 락 경로와 충돌 감지 유지)
  - `clearAutomatically = true`: 실행 후 영속성 컨텍스트를 비워, 다시 조회하면 DB의 최신 잔액을 읽음
- 데드락 방지: 두 계좌를 id 오름차순으로 UPDATE
- 거래 후 잔액(`balance_after`)은 UPDATE 직후 같은 트랜잭션에서 다시 조회해서 기록

## 다른 방식과의 차이

| | 잔액 계산 위치 | DB에 보내는 UPDATE |
|---|---|---|
| 락 없음 / 비관적 락 / 낙관적 락 | Java (`account.debit()`) | `balance = ?` (계산이 끝난 값) |
| 원자적 UPDATE | DB | `balance = balance - ?` (계산식) |

## 실험 조건

- 출금 계좌에 100,000원 입금 후, 1,000원 이체 요청 100건을 스레드 32개로 동시 실행

## 결과

| 항목 | 값 |
|---|---|
| 성공 / 실패 | 100 / 0 |
| 출금 계좌 | 시작 100,000원 → 기대 0원 / 실제 0원 |
| 입금 계좌 | 시작 0원 → 기대 100,000원 / 실제 100,000원 |
| 처리 시간 | 1,354ms (1회 측정) |

원본 출력:
```
========== 동시성 실험 결과 (원자적 UPDATE) ==========
요청 수          : 100
성공 / 실패      : 100 / 0
출금 계좌 기대 잔액 : 0  →  실제: 0
입금 계좌 기대 잔액 : 100000  →  실제: 100000
처리 시간        : 1354 ms
====================================================
```
(출력의 `기대 잔액 → 실제`는 "기대한 최종 잔액"과 "실제 최종 잔액"을 나란히 보여 주는 것)

## 분석

- 갱신 손실 없음: DB가 실행 시점의 최신 잔액으로 계산하므로 덮어쓰기가 발생하지 않음
- 같은 계좌의 UPDATE는 행 배타 락 때문에 여전히 한 번에 하나씩 처리됨
- 그런데도 비관적 락(2,641ms, 1회)보다 빨랐던 이유(추정)
  - 비관적 락: `SELECT ... FOR UPDATE` 시점부터 락을 잡아, 계좌 조회까지 순서대로 처리
  - 원자적 UPDATE: 계좌 조회는 락 없이 동시에 하고, UPDATE 시점부터 락을 잡음
  - → 락을 잡고 있는 구간이 더 짧음
- 단점: `Account.debit()`에 있던 규칙(금액 > 0, 사용 중인 계좌, 잔액 부족)이 서비스와 SQL로 흩어짐
  - 규칙이 한 곳(엔티티)에 모여 있지 않아, 규칙이 바뀌면 여러 곳을 고쳐야 함
- 처리 시간은 1회 측정값이므로, 방식 간 비교는 반복 측정 후 판단

## 예측과 비교

- 실행 전 예측: 100건 모두 성공 / 비관적 락보다 느릴 것 ("100건을 하나씩 처리해야 하니까")
- 결과: 성공 건수는 예측과 같음. 처리 시간은 예측과 달리 약 절반
- 배운 점: "하나씩 처리된다"는 것은 맞지만, 속도를 결정하는 것은 "락을 잡고 줄 서는 구간이 얼마나 긴가"

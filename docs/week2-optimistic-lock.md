# 2주차 (2): 낙관적 락으로 갱신 손실 해결

- 실험 일시: 2026-10-27
- 테스트: `TransferOptimisticLockTest` (재시도 없음 / 재시도 있음 2개)
- 환경: Spring Boot 4.1.2, MySQL 8.4 (Testcontainers), 격리 수준 REPEATABLE READ, HikariCP 기본 설정(커넥션 10개)

## 적용 방법

- Account 엔티티에 `@Version` 필드 추가 (UPDATE 시 `WHERE id = ? AND version = ?` 조건 자동 추가)
- 그사이 다른 트랜잭션이 먼저 수정했으면 수정 건수 0 → `OptimisticLockingFailureException` 발생 → 트랜잭션 롤백
- 재시도는 별도 클래스(`OptimisticLockTransferFacade`)에서 담당
  - 이유: Spring의 `@Transactional`은 다른 객체에서 들어오는 호출에만 적용되므로, 같은 클래스 안에서 재시도하면 새 트랜잭션이 시작되지 않음
  - 최대 100회 시도, 실패 시 10~50ms 랜덤 대기 후 재시도

## 실험 조건

- 출금 계좌에 100,000원 입금 후, 1,000원 이체 요청 100건을 스레드 32개로 동시 실행
- 두 테스트는 같은 테스트 DB를 순서대로 사용 (재시도 없음 → 재시도 있음)

## 결과

| 항목 | 재시도 없음 | 재시도 있음 |
|---|---|---|
| 성공 / 실패 | 10 / 90 | 100 / 0 |
| 전체 재시도 횟수 | - | 784 |
| 잔액 정확성 (성공 건수 기준) | 일치 | 일치 |
| 처리 시간 | 372 ms (1회 측정) | 2,493 ms (1회 측정) |

## 분석

- 재시도 없음: 100건 중 10건만 성공, 90건은 충돌로 실패하고 롤백됨
  - 1주차(락 없음)와 반영 건수는 같지만(10건), 1주차는 나머지 90건을 "성공"으로 응답하고 덮어썼고, 낙관적 락은 90건을 "실패"로 정직하게 응답함
  - 성공한 10건만큼은 잔액이 정확히

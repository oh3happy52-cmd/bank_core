# 1주차: 락 없는 이체의 갱신 손실(Lost Update) 재현

- 실험 일시: 2026-10-26
- 테스트: `TransferConcurrencyTest.락_없이_동시에_100번_이체하면_잔액이_틀어진다`
- 환경: Spring Boot 4.1.2, MySQL 8.4 (Testcontainers), 격리 수준 REPEATABLE READ, HikariCP 기본 설정

## 실험 조건

- 출금 계좌(100-0001)에 100,000원 입금 후 시작
- 출금 계좌 → 입금 계좌(100-0002)로 1,000원 이체 요청 100건을 동시에 실행
- 스레드 32개, 락 없음 (`@Version` 비활성화)

## 결과

| 항목 | 기대 | 실제 |
|---|---|---|
| 성공 / 실패 | 100 / 0 | 100 / 0 |
| 출금 계좌 잔액 | 0원 | 90,000원 |
| 입금 계좌 잔액 | 100,000원 | 10,000원 |
| 두 계좌 잔액 합계 변화 | 0원 | 0원 |

원본 출력:
```
========== 동시성 실험 결과 (락 없음) ==========
요청 수          : 100
성공 / 실패      : 100 / 0
김철수 기대 잔액 : 0  →  실제: 90000
이영희 기대 잔액 : 100000  →  실제: 10000
사라진/생긴 돈   : 0
===============================================
```

## 분석

- 100건 모두 성공 응답을 반환했지만 실제 잔액에는 10건만 반영됨
- 여러 트랜잭션이 같은 시점의 잔액을 읽고 각자 계산한 값으로 UPDATE하여, 나중에 커밋한 트랜잭션이 앞선 결과를 덮어씀 (Lost Update)
- 한 트랜잭션이 두 계좌를 함께 덮어써서 잔액 합계는 일치함
  → 잔액 합계 검증만으로는 탐지 불가
  → 원장(ledger_entry 200행)과 잔액을 대조해야 불일치를 발견할 수 있음
- 반영 건수가 10건인 이유는 DB 커넥션 풀 크기(기본 10)와 관련 있을 것으로 추정. 2주차에 풀 크기를 바꿔 검증 예정

## 참고: 실험을 위해 바꾼 점

- 잔액 UPDATE를 신청서 INSERT보다 먼저 실행 (`accountRepository.flush()`)
- 이유: 신청서 INSERT 시 외래 키 검사로 계좌 행에 공유 락이 걸려, 동시 요청 간 데드락이 먼저 발생하기 때문. 이번 실험은 갱신 손실만 분리해서 관찰하려는 목적
- 데드락은 2주차에 별도로 다룸

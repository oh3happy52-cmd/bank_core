# 2주차 (4): 잠금 순서와 데드락

- 실험 일시: 2026-10-27
- 테스트: `TransferDeadlockTest`
- 환경: Spring Boot 4.1.2, MySQL 8.4 (Testcontainers), 격리 수준 REPEATABLE READ

## 데드락이란

두 트랜잭션이 각자 행 하나씩 잠근 채로, 상대가 잠근 행을 기다리며 둘 다 진행하지 못하는 상태.

| 순서 | 트랜잭션 1 (A→B) | 트랜잭션 2 (B→A) |
|---|---|---|
| 1 | A 잠금 | B 잠금 |
| 2 | B 잠금 대기 (트랜잭션 2가 보유) | A 잠금 대기 (트랜잭션 1이 보유) |

MySQL은 데드락을 감지하면 한쪽 트랜잭션을 롤백시킴 (`Deadlock found when trying to get lock`).

## 실험 조건

- A→B 1,000원 이체 50건 + B→A 1,000원 이체 50건을 스레드 32개로 동시 실행
- 비관적 락(`SELECT ... FOR UPDATE`)으로 두 계좌를 잠근 뒤 잔액 이동
- 첫 번째 잠금 후 50ms 대기 (엇갈림이 생길 구간을 넓혀 결과를 분명하게 관찰하기 위함, 두 실험 동일 조건)
- 실험 코드는 테스트 폴더에만 둠 (`DeadlockExperimentService`)

## 결과

| | ① 보내는 계좌부터 잠금 | ② 계좌번호 작은 쪽부터 잠금 |
|---|---|---|
| 성공 | 50건 (A→B 26 / B→A 24) | 100건 |
| 데드락으로 실패 | 50건 | 0건 |
| 잔액 정확성 | 일치 | 일치 |

원본 출력:
```
========== 데드락 실험: ① 보내는 계좌부터 잠금 (순서 안 맞춤) ==========
요청 수            : A→B 50건 + B→A 50건
성공               : A→B 26건 / B→A 24건
데드락으로 실패     : 50건
기타 실패          : 0건
A 계좌 : 시작 100000 → 기대 98000 / 실제 98000
B 계좌 : 시작 100000 → 기대 102000 / 실제 102000

========== 데드락 실험: ② 계좌번호 작은 쪽부터 잠금 (순서 맞춤) ==========
요청 수            : A→B 50건 + B→A 50건
성공               : A→B 50건 / B→A 50건
데드락으로 실패     : 0건
기타 실패          : 0건
A 계좌 : 시작 198000 → 기대 198000 / 실제 198000
B 계좌 : 시작 202000 → 기대 202000 / 실제 202000
```

## 분석

- 잠금 순서가 요청 방향에 따라 달라지면, 양방향 동시 이체에서 데드락이 발생함
- 모든 트랜잭션이 같은 순서(계좌번호 오름차순)로 잠그면, 나중 트랜잭션은 아무 행도 잡지 않은 채 대기하므로 데드락이 구조적으로 생기지 않음
- 데드락으로 실패한 트랜잭션은 전부 롤백되어 잔액 정합성은 유지됨
- 단, 실패한 요청은 사용자에게 오류로 돌아가므로 서비스 품질 문제가 됨
- 50ms 대기를 인위적으로 넣은 실험이므로 실패 비율(50%)이 실제 서비스의 비율을 뜻하지는 않음

## 적용

- 실제 이체·입금 API는 `lockInOrder()`로 계좌번호 오름차순 잠금을 사용
